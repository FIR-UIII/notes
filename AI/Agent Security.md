# Безопасность AI-агентов

Область: системы, в которых LLM планирует и выполняет действия через инструменты (API, shell, браузер, MCP, другие агенты), имеет память и работает с частичной автономией.
Связанные файлы: [LLM Application Security](LLM%20Application%20Security.md) (база), [MCP Security](MCP%20Security.md), [Skill_security](Skill_security.md), [AI Coding Assistants](AI%20Coding%20Assistants%20Security.md).
Связанные заметки по IAM: [Token Exchange](../AuthN/Token%20Exchange.md), [DPoP](../AuthN/Demonstrating%20Proof-of-Possession%20%28DPoP%29.md), [PAR & RAR](../AuthN/PAR%20RFC9126%20&%20RAR%20RFC9396.md), [SPIFFE](../AuthN/SPIFFE.md), [Client Credentials](../AuthN/Client%20Credentials.md).

Маппинг на [OWASP Top 10 for Agentic Applications 2026](https://genai.owasp.org/initiatives/agentic-security-initiative/):

## Ключевые модели угроз

**Lethal trifecta** (S. Willison). Агент опасен, если одновременно:
1. имеет доступ к приватным данным,
2. обрабатывает недоверенный контент,
3. может отправлять данные наружу (сеть, email, комментарии, создание PR, рендер ссылок).

**Agents Rule of Two** (Meta, 2025). Сессия агента без участия человека должна иметь **не более двух** свойств из трёх: [A] обрабатывает недоверенный ввод, [B] имеет доступ к чувствительным системам или данным, [C] меняет состояние или общается вовне. Если нужны все три, то действие подтверждает человек или сессия перезапускается в урезанном режиме.

Реальные примеры: GitHub MCP (2025): вредоносный issue в публичном репо заставлял агента сливать данные из приватных; EchoLeak (M365 Copilot, 2025): zero-click эксфильтрация через письмо. Также известны многочисленные эксфильтрации через рендер markdown-изображений в чат-агентах.

## Требования

### AG-A. Идентичность агента (ASI03)
- [ ] **AG-01** `MUST` У каждого агента своя non-human identity (NHI). Агенты не используют общие сервисные аккаунты, а для массовых экземпляров — identity на экземпляр или на сессию (workload identity: SPIFFE/SVID, k8s SA token, cloud workload identity federation).
- [ ] **AG-02** `MUST` Долгоживущих ключей API в конфиге агента, переменных окружения и промптах нет. Учётные данные короткоживущие, выдаются при запуске (secrets manager, OIDC federation) и ротируются.
- [ ] **AG-03** `MUST` Секреты не попадают в контекстное окно модели. Агент вызывает инструмент, а токен подставляет credential broker или прокси вне LLM. Модель не может «прочитать и пересказать» ключ.
- [ ] **AG-04** `MUST` Агент не наследует токены и полные права пользователя и не работает с привилегиями суперпользователя.
- [ ] **AG-05** `MUST` Действия от имени пользователя оформляются через делегирование: OAuth 2.0 Token Exchange (RFC 8693) с claim `act` (агент) и `sub` (пользователь), audience-restricted токены на конкретный ресурс (RFC 8707), минимальные scope, короткий TTL. Пробрасывать пользовательский токен как есть (token passthrough) нельзя.
- [ ] **AG-06** `SHOULD` Токены агента привязаны к ключу (DPoP / mTLS-bound), чтобы украденный токен нельзя было использовать.

### AG-B. Авторизация действий (ASI02, ASI03)
- [ ] **AG-07** `MUST` Разрешения строятся на основе **возможностей (capabilities)**, а не ресурсов: не `billing:write`, а `billing.refund.issue_under_50_usd`. Рекомендуется ReBAC + ABAC (OpenFGA/SpiceDB, Cedar, OPA).
- [ ] **AG-08** `MUST` Каждый вызов инструмента авторизуется policy engine вне LLM с учётом: identity агента + identity пользователя (чьё поручение) + параметры вызова + контекст (тенант, время, риск). Это защищает от confused deputy.
- [ ] **AG-09** `MUST` Для каждого агента задан явный allowlist инструментов. Параметры инструментов валидируются по схеме и ограничениям (суммы, домены, пути, получатели).
- [ ] **AG-10** `MUST` Подагент получает строгое подмножество прав родителя. Права не расширяются транзитивно по цепочке агентов.

### AG-C. Human-in-the-loop (ASI09)
- [ ] **AG-11** `MUST` Действия классифицированы по риску (чтение / обратимая запись / необратимое или внешнее). Необратимые, финансовые, внешние коммуникации и изменения прав требуют подтверждения человеком.
- [ ] **AG-12** `MUST` Подтверждение показывает **конкретное действие с фактическими параметрами**, взятыми из вызова инструмента, а не пересказ модели. Пример: «подтвердить возврат 2000 USD клиенту Jane Doe по заказу №12345», а не «подтвердить доступ к выставлению счетов?».
- [ ] **AG-13** `SHOULD` Для асинхронных агентов используется CIBA + Rich Authorization Requests (RAR). Когда операция превышает автономный порог, бэкенд агента отправляет в IAM запрос CIBA с `authorization_details`, и пользователь получает push на зарегистрированное устройство. После подтверждения агент получает токен, привязанный к этому конкретному действию.
- [ ] **AG-14** `SHOULD` Защита от approval fatigue: группировка, пороги, отказ по умолчанию по таймауту, периодический аудит автоматически одобренных действий.

### AG-D. Архитектура против prompt injection (ASI01)
- [ ] **AG-15** `MUST` Для каждого агента проверено правило Rule of Two / lethal trifecta. Если все три свойства присутствуют, это зафиксировано в модели угроз с компенсирующими мерами (HITL, ограничение egress).
- [ ] **AG-16** `MUST` Результаты инструментов, документы, веб-страницы и письма считаются недоверенными данными, а не инструкциями. Агент не может по указанию из данных расширить свою цель или набор инструментов.
- [ ] **AG-17** `SHOULD` Применяются паттерны изоляции: **plan-then-execute** (план фиксируется до чтения недоверенных данных), **dual LLM / CaMeL** (привилегированная модель не видит сырых недоверенных данных, только ссылки и переменные), **action-selector**, контекстная минимизация.
- [ ] **AG-18** `SHOULD` Отслеживание происхождения данных (taint tracking). Данные из недоверенного источника не могут без подтверждения стать аргументом чувствительного инструмента (получатель письма, URL, команда).

### AG-E. Исполнение кода и окружение (ASI05)
- [ ] **AG-19** `MUST` Код, сгенерированный агентом, и shell-команды выполняются в изолированной песочнице: gVisor, Firecracker/Kata microVM, минимум — rootless-контейнер с `--network=none`, `--read-only`, `--cap-drop=ALL`, лимитами CPU/RAM/PID/времени. Окружение одноразовое.
- [ ] **AG-20** `MUST` Egress агента идёт через прокси с allowlist доменов. Произвольный исходящий трафик запрещён (это канал эксфильтрации).
- [ ] **AG-21** `MUST` Доступ к файловой системе ограничен рабочим каталогом. Нет доступа к `~/.ssh`, `~/.aws`, `.env`, сокету Docker, метаданным облака (169.254.169.254).

### AG-F. Память и контекст (ASI06)
- [ ] **AG-22** `MUST` Долговременная память изолирована по пользователю и тенанту. Каждая запись хранит происхождение (кто или что записал, из какого источника, когда).
- [ ] **AG-23** `MUST` Запись в память из недоверенного контента валидируется. Инструкции и «правила поведения» в память из данных не записываются.
- [ ] **AG-24** `MUST` В памяти нет секретов. Пользователь и администратор могут просмотреть и очистить память, у записей есть TTL.
- [ ] **AG-25** `SHOULD` Файлы памяти и инструкций (memory.md, AGENTS.md и т.п.) защищены от изменения самим агентом без ревью или подписаны (см. [Skill_security](Skill_security.md)).

### AG-G. Межагентное взаимодействие (ASI07)
- [ ] **AG-26** `MUST` Взаимная аутентификация агентов (mTLS / SPIFFE, подписанные JWT). Сообщения от другого агента — недоверенный ввод.
- [ ] **AG-27** `SHOULD` A2A: Agent Card подписаны и проверяются, capabilities удалённого агента сверяются с allowlist, подмена карточки отслеживается.

### AG-H. Устойчивость и контроль (ASI08, ASI10)
- [ ] **AG-28** `MUST` Лимиты на шаги, время, токены, стоимость и число вызовов инструментов на задачу. Работают обнаружение циклов и circuit breaker на сбоящие инструменты.
- [ ] **AG-29** `MUST` Kill switch: мгновенная остановка агента или класса агентов с отзывом всех его токенов.
- [ ] **AG-30** `MUST` Полная трассировка (OpenTelemetry GenAI semantic conventions): промпт, план, вызовы инструментов с параметрами, решения policy engine, подтверждения. Неизменяемый журнал аудита связывает каждое действие с человеком-принципалом.
- [ ] **AG-31** `SHOULD` Поведенческий baseline агента и алерты на отклонения: новые инструменты, домены, объёмы данных, время.

### AG-I. Supply chain и жизненный цикл (ASI04)
- [ ] **AG-32** `MUST` Инвентаризация агентов: владелец, назначение, модель, инструменты, MCP-серверы, skills, права, данные. Неиспользуемые агенты выводятся из эксплуатации с отзывом identity.
- [ ] **AG-33** `MUST` Фреймворки (LangChain, LlamaIndex, AutoGen, CrewAI, OpenAI Agents SDK и др.), инструменты, промпты, MCP-серверы и skills закреплены по версиям и проходят SCA/ревью.
- [ ] **AG-34** `MUST` Модель угроз на каждого агента (рекомендуется CSA MAESTRO).
