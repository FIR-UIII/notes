 Go спроектирован как безопасный язык (memory-safe), но у него есть свои «слепые зоны» на уровне рантайма, структур данных и стандартной библиотеки, которые критично понимать при аудите кода или проектировании архитектуры распределенных систем.
Вот основные направления в internals Go, на которые стоит обратить внимание:
1. Data Races и Type Confusion (Гонка данных)
В Go data race — это не просто логическая ошибка. Из-за особенностей внутреннего устройства сложных типов, гонка данных может стать вектором эксплуатации.
 * Интерфейсы: Под капотом интерфейс в Go состоит из двух машинных слов: указателя на тип данных и указателя на сами данные (itable и data). Если две горутины одновременно читают и пишут в интерфейс, может произойти расхождение — программа прочитает указатель на тип от первой переменной, а данные — от второй. Это называется type confusion и потенциально дает злоумышленнику возможность добиться выполнения произвольного кода (RCE).
 * Срезы (Slices) и Строки: Срез состоит из трех слов (указатель на базовый массив, длина, вместимость). Гонка при конкурентном обновлении среза может дать приложению доступ к памяти за пределами выделенного буфера (Out-of-Bounds read/write).
2. Специфика Standard Library
Стандартная библиотека Go огромна и часто используется в enterprise-решениях без дополнительных оберток (например, при написании middleware).
 * HTTP Request Smuggling (net/http): Реализация HTTP-сервера в Go имеет свои особенности парсинга пробелов, переносов строк и некорректных заголовков. Разница в интерпретации протокола между сервером на Go и стоящим перед ним reverse-proxy (Nginx, Envoy, HAProxy) часто открывает путь для атак HTTP Desync и подмены запросов.
 * Обход нормализации путей (path vs path/filepath): Пакет path работает с логическими путями (например, URL-адресами), а filepath — с путями операционной системы. Использование path.Clean() для локальных файлов часто приводит к уязвимостям Path Traversal, особенно на Windows-системах, где обработка слешей (\ и /) и названий томов (C:) имеет специфические кейсы.
 * Парсинг XML и SSO (encoding/xml): Исторически пакет encoding/xml имел специфическое поведение при разборе пространств имен (namespaces) и вложенных комментариев. Это приводило к обходам проверки валидности XML Signature (XMLDSig) — критичной уязвимости для IAM-систем и провайдеров SAML-аутентификации.
3. Goroutine Leaks как вектор DoS
Это специфичная для Go архитектурная уязвимость. Горутины стоят очень дешево (создаются с минимальным стеком ~2 КБ), но если они блокируются навсегда, они оседают в памяти вместе со своими локальными переменными.
 * Механика: Если gRPC-метод или HTTP-обработчик ожидает данных из канала без таймаута, злоумышленник может инициировать тысячи медленных или обрываемых соединений. Зависшие горутины будут накапливаться, что быстро приведет к исчерпыванию памяти (OOM) и падению процесса (Denial of Service). Использование context.Context с жесткими Deadline обязательно на всех уровнях архитектуры.
4. Граница памяти: unsafe и cgo
Выход за пределы безопасного рантайма Go возвращает проблемы классического C/C++:
 * Пакет unsafe: Позволяет обходить систему типов Go и напрямую кастовать указатели. Неправильная арифметика unsafe.Pointer ведет к чтению чужой памяти.
 * Пересечение cgo: Сборщик мусора (GC) в Go в определенных ситуациях может перемещать объекты в памяти. Если передать указатель на Go-структуру в C-код без должной фиксации (pinning), и сборщик переместит объект в этот момент, C-код обратится к невалидной памяти, что вызовет Use-After-Free или Segmentation Fault.
5. Алиасинг срезов (Slice Aliasing)
Срезы в Go не хранят данные сами, а лишь указывают на скрытый «базовый массив» (underlying array).
Если создать несколько дочерних срезов из одного массива, функция append() к одному из них может не выделить новую память, а молча перезаписать элементы в исходном массиве, на которые всё еще ссылается другой срез. Это приводит к перезаписи соседних переменных в памяти и непреднамеренной утечке конфиденциальных данных (например, сессионных токенов) между разными контекстами выполнения.

Использование cgo (механизма вызова C-кода из Go) часто встречается в энтерпрайзе: криптография, PAM-модули, драйверы баз данных, высокопроизводительные хэши или интеграция с legacy-библиотеками.
Главная проблема cgo с точки зрения AppSec заключается в том, что граница между Go и C стирает гарантии безопасности обоих языков. Go теряет контроль над памятью, а C получает данные с неожиданной структурой.
Вот три основных вектора уязвимостей на стыке cgo с примерами.
1. Асинхронный Use-After-Free (Вина сборщика мусора)
Сборщик мусора (GC) в Go не просто удаляет старые объекты, он может перемещать их. В частности, стек горутины может динамически расти или сжиматься. При изменении размера стека Go копирует все переменные в новую область памяти и обновляет указатели.
C-код ничего не знает о перемещениях памяти в Go. Если вы передали указатель в C, и C-код сохранил его для отложенного использования (например, в глобальную переменную или передал в callback-поток), то когда Go переместит объект или удалит его, C-код обратится к невалидной памяти. Это классический Use-After-Free (UAF), ведущий к RCE.
Уязвимый код:
package main

/*
#include <stdio.h>
#include <stdlib.h>

int* global_ptr;

// C-код сохраняет указатель на будущее
void save_pointer(int* ptr) {
    global_ptr = ptr;
}

// Вызывается позже из другого контекста
void trigger_uaf() {
    if (global_ptr != NULL) {
        // УЯЗВИМОСТЬ: память по этому адресу уже могла быть освобождена
        // или перезаписана другими данными Go!
        printf("Значение: %d\n", *global_ptr); 
        *global_ptr = 999; // Перезапись чужой памяти (Memory Corruption / RCE)
    }
}
*/
import "C"
import (
	"fmt"
	"time"
	"unsafe"
)

func main() {
	go func() {
		// Локальная переменная на стеке горутины
		secretData := C.int(42)
		// Передаем указатель на стек Go в C-код
		C.save_pointer(&secretData)
	}()

	// Даем время горутине завершиться (стек очищается/переиспользуется)
	time.Sleep(1 * time.Second)

	// Триггерим использование указателя
	C.trigger_uaf()
}

> Как защищаться:
> Начиная с Go 1.21, появился тип runtime.Pinner. Он позволяет "приколоть" (pin) объект в памяти, запретив сборщику мусора перемещать или удалять его до вызова Unpin(). Альтернатива — выделять память через C.malloc, которая полностью управляется вручную и игнорируется GC Go.
> 
2. Утечка информации через отсутствие нуль-терминатора (Out-of-Bounds Read)
Строки и срезы (slice) в Go не оканчиваются нулевым байтом (\0). Они хранят свою длину отдельно. Строки в C обязательно должны заканчиваться нулевым байтом.
Если разработчик ради оптимизации (чтобы избежать аллокации памяти и копирования) кастует Go-строку напрямую в указатель C, возникает уязвимость, идентичная знаменитому Heartbleed: C-код будет читать память за пределами строки, пока случайно не встретит \0.
Уязвимый код:
package main

/*
#include <stdio.h>

// Ожидает классическую C-строку с \0 в конце
void process_token(char* token) {
    // УЯЗВИМОСТЬ: Чтение памяти до тех пор, пока не встретится 0x00
    printf("Processing: %s\n", token);
}
*/
import "C"
import (
	"unsafe"
)

func main() {
	// Строка в Go (в памяти за ней лежат другие данные)
	token := "auth_token_123"
	
	secretKey := "SUPER_SECRET_KEY_DO_NOT_LEAK"

	// ОПАСНАЯ ОПТИМИЗАЦИЯ: передача указателя на тело Go-строки напрямую
	// Мы берем адрес первого байта строки.
	ptr := (*C.char)(unsafe.Pointer(unsafe.StringData(token)))
	
	// Выведет: auth_token_123SUPER_SECRET_KEY_DO_NOT_LEAK... и так далее
	C.process_token(ptr)
}

> Как защищаться:
> Никогда не кастовать строки напрямую. Всегда использовать C.CString(goString). Эта функция выделяет новую память на стороне C, копирует туда данные и корректно добавляет \0. После использования эту память необходимо освободить: defer C.free(unsafe.Pointer(cStr)).
> 
3. Проброс C-уязвимостей через интерфейс Go (Buffer Overflow)
Go-сервис будет скомпрометирован, если вызываемая C-библиотека имеет классические уязвимости. Разработчики часто думают: «Мой веб-сервер написан на Go, значит он защищен от переполнения буфера». Но если HTTP-запрос передает payload в уязвимую C-функцию (например, для парсинга картинок, обработки XML или валидации сертификатов), атакующий получает RCE в контексте процесса Go.
Уязвимый код:
package main

/*
#include <string.h>
#include <stdio.h>

// Уязвимая функция из legacy C-библиотеки
void parse_user_input(char* input) {
    char buffer[16];
    // УЯЗВИМОСТЬ: Классическое переполнение буфера
    // Если input больше 16 байт, он перезапишет адрес возврата в стеке
    strcpy(buffer, input);
    printf("User input loaded.\n");
}
*/
import "C"
import (
	"unsafe"
)

func HandleRequest(userInput string) {
	// Безопасно конвертируем в C-строку
	cStr := C.CString(userInput)
	defer C.free(unsafe.Pointer(cStr))

	// Передаем безопасно созданную строку в НЕБЕЗОПАСНУЮ C-функцию.
	// Пейлоад из HTTP-запроса вызовет Segmentation Fault или RCE.
	C.parse_user_input(cStr) 
}

func main() {
	// Атакующий шлет длинную строку:
	payload := "AAAAAAAAAAAAAAAABBBBBBBBBBBBBBBB" // перезапишет RIP/RSP
	HandleRequest(payload)
}

Выводы для AppSec-аудита
При ревью архитектуры обращайте внимание на следующие паттерны поиска (grep/semgrep):
 * unsafe.Pointer в аргументах функций C.* — верный признак попытки избежать копирования (OOB Read).
 * Вызовы C.malloc или C.CString без последующего defer C.free — ведет к утечке памяти и Denial of Service (OOM Kill).
 * Передача в C структур, содержащих вложенные Go-указатели. Рантайм Go пытается ловить это (правила cgo pointers), вызывая панику при запуске, но асинхронное сохранение он не отследит.
