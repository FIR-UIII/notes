Кэш располагается между сервером и пользователем, как правило как часть инфраструктуры сервиса через CDN, где он сохраняет (кэширует) ответы на конкретные запросы, обычно на фиксированный период времени. 
Если другой пользователь затем отправляет аналогичный запрос, кэш просто предоставляет копию кэшированного ответа непосредственно пользователю, без какого-либо взаимодействия со стороны бэкэнда. 
Это значительно снижает нагрузку на сервер, уменьшая количество дублирующих запросов, которые ему приходится обрабатывать.
Кэши идентифицируют эквивалентные запросы, сравнивая предопределенное подмножество компонентов запроса, известных как «ключ кэша». Обычно он содержит строку запроса и Hostзаголовок. Компоненты запроса, не включенные в ключ кэша, называются «неключевыми».
На кеше такой ключ может выглядеть как `Cache key: https|GET|portswigger.net|/research?x=1` но пользователь этого не знает.

## Методология поиска уязвимостей
1. **Выбор Cache Oracle (Кэш-оракула):** Поиск кэшируемого эндпоинта, который позволяет явно определить статус кэша (hit/miss) через заголовки (напр., `CF-Cache-Status`) или время ответа. В идеале он должен отражать полный URL и параметры. Можно использовать https://github.com/PortSwigger/param-miner
2. **Анализ обработки ключей (Probe Key Handling):** Отправка серии запросов для выявления трансформаций, которые кэш применяет к ключу. Исследуется удаление query-параметров, удаление порта из заголовка `Host`, URL-декодирование и т.д.
3. **Эксплуатация (Exploit):** Связывание найденных расхождений кэша с "гаджетами" на бэкенде (например, reflected XSS, Open Redirect, или просто динамическое поведение ресурса), превращая их в высококритичные уязвимости.

## Ключевые техники и векторы
* **Атака через порт в Host:** Если кэш (например, Cloudflare, Fastly) исключает порт из ключа кэша, а бэкенд использует его для редиректов, можно закэшировать редирект на фейковый порт, вызвав DoS одним запросом.
* **Unkeyed Query (Некэшируемые параметры запроса):** Часто кэш игнорирует всю строку запроса (query string) при формировании ключа. Это маскирует уязвимые динамические параметры, так как сканеры уязвимостей не могут пробить кэш.
* **Методы пробития кэша (Cache-Busting):** 
  * Использование cache-buster в потенциально кэшируемых заголовках (например, `Origin`, `Accept`, `Accept-Encoding`).
  * Эксплуатация нормализации путей для создания уникального ключа: `//` (Apache), `/%2F` (Nginx), `/index.php/xyz` (PHP), `/(A(xyz))/` (.NET).
  * Использование HTTP-методов `PURGE` или `FASTLYPURGE`.

## Последствия (Impact)
* **Эскалация Reflected XSS в Stored XSS** — закэшированная XSS будет срабатывать у всех пользователей.
* Отравив кэш статических ресурсов (JS, CSS), можно внедрить вредоносный код для всех посетителей.
* Массовый DoS страниц сайта.
* Эксплуатация считавшихся ранее "неэксплуатируемыми" уязвимостей.
