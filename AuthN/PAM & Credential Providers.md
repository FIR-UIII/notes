### Windows: Credential Providers

В Windows за аутентификацию отвечает архитектура Credential Providers. Это COM-объект, реализованный в виде динамической библиотеки .dll. При разблокировке компьютера инициализируется внутри процесса LogonUI.exe как дочерний и формирует интерфейс пользователю. После того как пользователь ввел пароль/ОТР/приложил смарткарту - он отдает данные другому процессу LSASS.exe.
Сами находятся в C:\Windows\System32\*
Чтобы система (LogonUI) узнала о существовании провайдера, он должен быть зарегистрирован в системном реестре как COM-объект HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Authentication\Credential Providers\*
Каждая подпапка внутри этого ключа — это GUID (глобальный уникальный идентификатор) конкретного провайдера. 

Вариант 1. Запрос при каждой разблокировке:
Как работает: При каждом пробуждении экрана или выходе из блокировки (Win+L) Credential Provider сбрасывает состояние аутентификации и принудительно вызывает метод GetSerialization.
Реализация: В коде провайдера отключается кэширование сессионных токенов 2FA. Пользователь обязан приложить палец, вставить смарт-карту или ввести OTP-код каждый раз.

Вариант 2. Запрос только при входе / Кэширование:
Как работает: Второй фактор требуется только при первичном входе в систему (после перезагрузки или полного выхода из учетной записи Sign out). При разблокировке (Unlock) достаточно ввести только PIN-код или пароль (первый фактор).
Реализация: Сторонние решения (например, Duo или Yubikey Windows Login) используют кэширование жизненного цикла сессии (Session TTL). Провайдер проверяет идентификатор текущей сессии Windows (Session ID). Если для этого ID аутентификация 2FA уже была успешно пройдена в течение заданного времени (например, 8 часов), шаг 2FA при разблокировке пропускается.
Важно:  Нельзя разрешить второму пользователю войти без 2FA только потому, что первый пользователь успешно ввел свой OTP 10 минут назад. Поэтому Кэш TTL должен быть строго привязан к комбинации [Имя Пользователя + Session ID].

##### Как настроить Windows: Credential Providers 
Win+R > regedit [Enter] > `Компьютер\HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows\CurrentVersion\Authentication\Credential Provider Filters` > Список провайдеров [выбрать нужный] > исправить атрибуты

Какие сценарии обрабатываются:
Logon (Вход): Создание сессии с нуля. Пользователя еще нет в памяти компьютера, его рабочий стол не запущен, программы закрыты. Системное событие API: WTS_SESSION_LOGON, в журнале Event ID 4624. Credential Provider обязан собрать данные и передать их в LSASS для полной проверки подлинности.

Unlock (Разблокировка): Возврат в уже существующую сессию. Пользователь уже в системе, все его программы (браузер, документы, игры) запущены и «заморожены» на заднем плане за экраном блокировки. Системное событие API: WTS_SESSION_UNLOCK. В журнале Event ID 4801. Credential Provider может использовать кэширование (TTL) и пропустить проверку второго фактора.

Logoff (Выход). Системное событие API: WTS_SESSION_LOGOFF. Event ID 4647: Выход, инициированный пользователем (User-initiated logoff) или Event ID 4634: Сессия была завершена (An account was logged off)


### Linux: PAM (Pluggable Authentication Modules)
В Linux подсистема PAM управляет аутентификацией через разделение на разные типы конфигурационных файлов. За вход отвечают файлы вроде /etc/pam.d/gdm-password (для графического входа) или /etc/pam.d/login (для консоли), а за разблокировку экрана — /etc/pam.d/gdm-lock, /etc/pam.d/cinnamon-screensaver или /etc/pam.d/swaylock.

Вариант 1. Запрос при каждой разблокировке:
Как работает: Модуль 2FA (например, pam_google_authenticator.so или pam_yubico.so) жестко прописывается в конфигурационный файл экранного заставщика (экранной блокировки).
Реализация: В файле /etc/pam.d/gdm-lock (или аналогичном для вашего DE) строка с вызовом 2FA-модуля активна. 
Пример: auth required pam_google_authenticator.so. Каждая попытка снять блок вызывает выполнение этого модуля.

Вариант 2. Запрос только при входе / Кэширование:
Как работает: При разблокировке экрана запрашивается только стандартный пароль Linux, а OTP/токен не требуется если запрос выполнен в течении определенного периода.
Реализация: Администратор настраивает 2FA только в файлах первичного входа (/etc/pam.d/common-auth или system-auth), но исключает его из правил для скринсейверов (gdm-lock, kde, xscreensaver). Системы вроде Yubico также поддерживают параметр grace_period прямо внутри модуля PAM — если токен проверялся менее N секунд назад, повторный запрос опускается.

##### Как настроить в Linux
В отличие от Windows, где один и тот же Credential Provider должен сам внутри себя проверять контекст (CPUS_LOGON или CPUS_UNLOCK), в Linux это разделение настроено на уровне конфигурационных файлов PAM, которые лежат в директории /etc/pam.d/.

/etc/pam.d/gdm-password — правила для первичного графического входа<br>
./etc/pam.d/gdm-lock — правила для разблокировки экрана GNOME<br>
./etc/pam.d/sshd — правила для входа по SSH.<br>

Вариант 1. Запрос 2FA всегда (и при входе, и при разблокировке)
```gdm-password и gdm-lock 
auth required pam_google_authenticator.so
```

Вариант 2. Запрос только при первичном входе (Кэширование / TTL)
```gdm-password и gdm-lock
auth required pam_yubico.so id=1234 key=xxxx grace_period=3600
```
Либо добавляем строку `auth required pam_google_authenticator.so` в файл /etc/pam.d/gdm-password, но НЕ добавляем её в /etc/pam.d/gdm-lock. В итоге при включении ПК система потребует пароль + OTP, а при разблокировке экрана gdm-lock обратится только к стандартному модулю пароля pam_unix.so. Второй фактор при разблокировке запрашиваться не будет вообще.

Для фиксации событий можно образаться к демону `systemd-logind`
